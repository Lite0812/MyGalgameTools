# HXB 文件解析说明

本文根据 `export-for-ai/decompile` 中的反编译结果整理，说明 EXE 对 `.hxb` 文件的读取、识别、解密和内存组织方式。重点函数是 `sub_40E930`，它负责真正识别 HXB 格式；资源读取入口在 `sub_41EEE0`/`sub_41EA80`。

## 1. 入口链路

HXB 不是直接按文件扩展名分发解析，而是先由通用资源读取层把资源读到内存，再尝试按不同格式识别。

主要链路如下：

```text
sub_40EBA0
  -> sub_41EEE0          读取一个资源到内存
  -> sub_40E930          尝试按 HXB 解析
  -> sub_40EAB0/sub_40E8C0  管理当前 HXB 包对象

sub_40EFF0(resource_id)
  -> sub_41EEE0          读取指定资源
  -> sub_40E930          若资源本身是 HXB，则作为 HXB 包
  -> 其他图片/音频/原始资源解析
```

对应证据：

- `sub_40EBA0` 读取资源后调用 `sub_40E930(v4, v0)`，成功后把结果放入全局 `dword_4999C0`。
- `sub_40EFF0` 对单个资源 ID 载入资源，也会先调用 `sub_40E930`；失败后才尝试 BMP、图像、音频或原始资源。
- `sub_413480` 也会读取资源后调用 `sub_40E930`，再通过 `sub_40EB30` 挂到当前 HXB 包链表。

## 2. 通用资源读取层

`sub_41EEE0` 负责把资源读成内存块。它内部先调用 `sub_41EA80` 得到：

- 文件句柄；
- 资源起始偏移；
- 资源大小；
- 是否需要解压标记。

`sub_41EA80` 同时支持两类资源来源：

1. 直接文件读取；
2. DDP2/DDP3 资源包内读取。

DDP2/DDP3 的 magic 常量在 `sub_41EA80` 中判断：

```text
0x32504444 = "DDP2"
0x33504444 = "DDP3"
```

如果资源来自 DDP 包，`sub_41EA80` 会从包索引中定位目标资源的偏移、压缩后大小和解压后大小；`sub_41EEE0` 看到需要解压时，会调用 `sub_41E7A0` 做解压。`sub_41E7A0` 是一个 LZ 风格的回溯复制解压器。

因此，`sub_40E930` 接收到的 HXB 数据通常已经是资源读取层处理后的完整 HXB 文件内容，不是 DDP 包内的原始压缩块。

## 3. HXB 头部格式

`sub_40E930(a1, a2)` 中：

- `a1` 是输入数据长度；
- `a2` 是输入数据指针。

函数首先要求 `a1 >= 16`，然后检查 HXB 头。头部至少 16 字节：

```text
offset  size  说明
0x00    1     固定 'D' (0x44)
0x01    1     固定 'D' (0x44)
0x02    1     变体标记。若为 'W' 且 0x03 为 'u'，表示 Unicode/Wide 变体
0x03    1     变体标记。与 0x02 一起参与 DDWu 判断
0x04    1     固定 'H' (0x48)
0x05    1     固定 'X' (0x58)
0x06    1     固定 'B' (0x42)
0x07    1     必须为 0
0x08    3     文件总长度，24-bit big-endian，必须等于输入长度 a1
0x0B    1     扩展头/名称区标记，非 0 时后面有名称字符串
0x0C    4     原样保存的未知字段
0x10    ...   加密后的主体 dword 数据
```

长度字段的计算方式来自 `sub_40E930`：

```c
len24 = data[10] | ((data[8] << 8 | data[9]) << 8)
```

也就是：

```text
len24 = data[8] << 16 | data[9] << 8 | data[10]
```

例如仓库中的 `hxb/h000.hxb` 开头为：

```text
44 44 57 75 48 58 42 00 00 24 91 00 ...
```

可解释为：

```text
DDWuHXB\0
长度 = 0x002491 = 9361 字节
扩展头标记 = 0
```

## 4. DDWu 与文本编码标记

`sub_40E930` 并不强制第 2、3 字节一定是 `Wu`。它只检查：

```text
data[0] == 'D'
data[1] == 'D'
data[4] == 'H'
data[5] == 'X'
data[6] == 'B'
data[7] == 0
```

然后额外记录：

```text
is_wide = data[2] == 'W' && data[3] == 'u'
```

若 `is_wide` 为真，并且 `data[0x0B] != 0`，函数会在 offset `0x10` 后按 UTF-16LE 风格连续跳过两个 0 结尾宽字符串；否则按普通 C 字符串跳过两个 0 结尾窄字符串。

这两个字符串之后的位置会成为 HXB 主体数据起点。若 `data[0x0B] == 0`，主体数据起点固定为 `0x10`。

## 5. 主体 dword 解密

HXB 从 offset `0x10` 开始的主体数据按 4 字节一组解密。`sub_40E930` 分配新对象后，把输入头部的前 16 字节保存到对象内部，再对后续 dword 执行 XOR 变换：

```c
key = ((file_size + 455497) * ((32 * file_size) ^ 0xA5)) ^ 0x34A9B129;
plain_dword = cipher_dword ^ key;
```

这里的 `file_size` 就是输入长度 `a1`，也是头部 offset `0x08..0x0A` 的 24-bit 长度。

反编译代码中的表达式是：

```c
*v9 = ((a1 + 455497) * ((32 * a1) ^ 0xA5)) ^ 0x34A9B129 ^ *(int *)src;
```

注意事项：

- 运算应按 32-bit 整数截断处理；
- 解密单位是 little-endian dword；
- 解密从 offset `0x10` 开始；
- 反编译中循环次数为 `(a1 - 13) / 4`，会覆盖从 `0x10` 之后的主体 dword 区。实际实现时需要特别确认尾部不足 4 字节时的处理，避免越界或漏字节。

## 6. 解析后的内存对象布局

`sub_40E930` 不只是返回解密后的 HXB 数据，而是构造一个较大的资源包对象。关键字段如下：

```text
对象基址 + 0x00000   当前主体读取偏移，初始化为 data_start
对象基址 + 0x00004   指向解密后的 HXB 数据副本，实际为 对象基址 + 263904
对象基址 + 0x00008   HXB 文件长度
对象基址 + 0x0000C   HXB 主体数据起点 data_start

对象基址 + 263224    资源槽表，56 项，每项 12 字节
对象基址 + 263900    is_wide 标记，DDWu 时为 1
对象基址 + 263901    当前对象是否已挂入/共享的状态标记
对象基址 + 263902    释放策略标记
对象基址 + 263903    扩展头/名称区标记，即 data[0x0B] != 0
对象基址 + 263904    解密后的 HXB 数据副本起点
对象基址 + 263896    链表 next，连接到上一个 dword_4999C0
```

资源槽表长度为 `0x2A0 = 672` 字节，即 `56 * 12`。这与 `sub_40EFF0` 中访问资源 ID `200..255` 的逻辑对应：

```text
slot = hxb_object + 260824 + resource_id * 12
```

当 `resource_id == 200` 时，正好落到 `hxb_object + 263224`。因此 HXB 包给高编号资源 `200..255` 提供一组局部资源槽。

## 7. HXB 包链表与生命周期

全局变量 `dword_4999C0` 保存当前 HXB 包对象链表头。

相关函数：

- `sub_40EBA0`：读取主 HXB 包，解析成功后设为 `dword_4999C0`；
- `sub_40EB30`：把新的 HXB 包挂入当前链表，可选择保留旧包作为 next；
- `sub_40E8C0`：清理当前 HXB 包链表；
- `sub_40EAB0`：复制一个 HXB 对象，并清空缓存/资源槽状态，用于避免直接修改共享对象。

这说明 HXB 更像是一个运行时资源包/上下文对象，不只是单个资源文件。游戏会切换或叠加 HXB 包，然后从其中解析后续资源。

## 8. 与音频/其他资源的关系

音频读取链路在 `sub_40A8F0`、`sub_4089C0`、`sub_41FC60`、`sub_41FF00` 一带。这里会识别 OggS、RIFF/WAVE 等音频格式，或者从资源读取层得到的数据流中解析 Ogg 页。

这条链路与 HXB 的关系是：

- HXB 包对象提供资源槽和当前资源上下文；
- 单个资源读取出来后，`sub_40EFF0` 再决定它是 HXB、图片、音频还是原始数据；
- 若资源是音频，才进入 `sub_40A240`/`sub_40A8F0` 等音频解析。

因此不要把 HXB 主体直接当作 Ogg 或 RIFF；HXB 是上层资源容器/资源上下文，内部资源可能再包含音频、图片或其他二进制块。

## 9. HXB 脚本 VM 总览

解密后的 HXB 主体不只是资源目录，还包含一套字节码脚本。脚本运行时的核心入口是：

```text
sub_410580        主运行循环
  -> sub_410FC0   单步取指、分发 opcode
       -> funcs_411044[opcode]
       -> 各 opcode handler
            -> sub_40D920  解析表达式/参数
```

`sub_410580` 在当前 HXB 包对象存在、且没有全局停止标记时，反复调用 `sub_410FC0`。因此 `sub_410FC0` 可以视为 HXB VM 的单步解释器。

当前活动 HXB 包由全局 `dword_4999C0` 指向。对象开头几个字段直接参与 VM 执行：

```text
对象 + 0x0000  当前 PC / 主体读取偏移
对象 + 0x0004  解密后的 HXB 数据基址
对象 + 0x000C  主体 data_start，进入脚本或包时用于重置 PC
```

取指流程来自 `sub_410FC0`：

1. 若对象的 `+263903` 扩展头标记为真，先从当前 PC 读取 2 字节并保存到 `object[65805]`，然后 PC 前进 2。这个字段更像是扩展模式下的行号、段号或调试/脚本块标记，具体语义还要结合样本继续验证。
2. 从 `base + PC` 读取 1 字节 opcode。
3. PC 前进 1。
4. 若 opcode 为 `0xFF`，结束当前 HXB 包上下文：要么释放当前包，要么退回链表中的上一个包。
5. 否则把 opcode 保存到 `byte_497110`，再调用 `funcs_411044[opcode]`。

因此，顶层指令格式至少是：

```text
[可选 2 字节扩展前缀] [1 字节 opcode] [handler 自己解析的操作数...]
```

`0xFF` 在两个层级都很重要：

- 顶层 opcode `0xFF`：结束当前脚本包/上下文；
- 表达式流中的 `0xFF`：结束当前表达式，由 `sub_40D920` 消费并把 PC 更新到表达式之后。

## 10. 表达式/参数 VM：sub_40D920

`sub_40D920` 是大量 opcode handler 共用的参数解析器。它从当前 `base + PC` 开始读取一段表达式字节码，直到遇到 `0xFF` 为止。解析结束时，它会把当前 HXB 对象的 PC 设置为 `0xFF` 后一字节。

调用方通常传入一个 3 个字段的临时结构：

```text
result[0] = 求值后的数值，或字符串指针
result[1] = 原始变量索引/立即数辅助值
result[2] = 类型标志；低字节非 0 表示字符串，高字节表示变量空间/左值来源
```

表达式 VM 是一个简单的栈式求值器。内部栈项大致是三元组：

```text
(value, raw_or_index, type_flags)
```

每个表达式 token 用高 4 位分组、低 4 位作子码：

```text
token_hi = token & 0xF0
token_lo = token & 0x0F
```

### 10.1 数值立即数与数值变量

当 token `< 0x40` 时，表示数值立即数或数值变量读取。

`token_hi == 0x00` 时偏向立即数：

```text
lo 0x0..0x7   直接表示 0..7
lo 0x8..0xC   表示负小整数，计算为 7 - lo，即 -1..-5
lo 0xD        后接 1 字节小立即数
lo 0xE        后接 2 字节 big-endian 数值
lo 0xF        后接 4 字节 big-endian 数值
```

`token_hi != 0x00` 时表示读取数值变量。若低位小于 `0xE`，低位本身就是变量索引；若为 `0xE` 或 `0xF`，后续分别读取 1 字节或 2 字节扩展索引。

数值变量读取通过 `sub_40D540(type, index)` 完成，目前确认的空间如下：

```text
0x10 / type 16   dword_499980，结果寄存器/参数寄存器数组
0x20 / type 32   当前 HXB 对象内的局部数值变量，对象 + 4 + index * 4
0x30 / type 48   dword_499978，全局数值表
```

### 10.2 字符串立即数与字符串变量

当 `token_hi >= 0x80` 时，表示字符串值。

```text
0x80          内联字符串，0 结尾
0x90          字符串变量空间 19，即 dword_499984
0xA0          字符串变量空间 17，即当前 HXB 对象局部字符串
0xB0          字符串变量空间 18，即 dword_49997C
```

内联字符串的解码受 HXB 对象的 `is_wide` 标记影响：

- `is_wide != 0`：按 UTF-16LE 风格读取，直到 16-bit `0x0000`；
- `is_wide == 0`：按窄字符串读取，再用 `MultiByteToWideChar` 转成宽字符串。

字符串变量读取通过 `sub_40D660(index, type)` 完成，确认映射如下：

```text
type 17   当前 HXB 对象局部字符串，对象 + 1040 + 1024 * index
type 18   dword_49997C + 1024 * index
type 19   dword_499984 + 1024 * index
```

字符串变量写入通过 `sub_40D710(value, type, index)` 完成。

### 10.3 一元操作与变量间接读取

`token_hi == 0x70` 是一元操作组。

低位 `0x0..0x6` 是普通一元函数：

```text
0x70  取负：-x
0x71  逻辑非：x == 0
0x72  随机数：rand() % x
0x73  sin，角度单位约为 1/100 度，结果乘 10000
0x74  cos，角度单位约为 1/100 度，结果乘 10000
0x75  反三角/角度换算相关，结果归一到 0..35999
0x76  sqrt，结果乘 10000
```

低位 `0x8..0xB` 会把栈顶值当作索引，再去读取某个数值变量空间；低位 `0xC..0xF` 类似地读取字符串变量空间。这说明表达式 VM 支持“索引由表达式计算出来”的间接变量访问。

### 10.4 比较、算术、逻辑与字符串拼接

`token_hi == 0x50` 是比较操作，对栈顶两个值求比较，结果为数值布尔值：

```text
0x50  ==
0x51  !=
0x52  <
0x53  <=
0x54  >
0x55  >=
```

若任一操作数是字符串，会转成字符串后用 `lstrcmpW` 比较。

`token_hi == 0x60` 是二元运算组：

```text
0x60  加法；若有字符串则表示字符串拼接
0x61  减法
0x68  乘法
0x69  除法
0x6A  取模
0x6B  按位与
0x6C  按位或
0x6D  逻辑与
0x6E  逻辑或
```

这里有一个不连续点：加减使用 `0x60/0x61`，乘除模等使用 `0x68..0x6E`。中间 `0x62..0x67` 在当前反编译逻辑中没有明显处理分支，可能是保留、废弃，或由编译器生成时不使用。

当 token 带 `0x40` 位、且不属于上面的比较/运算组时，会进入赋值/更新逻辑。数值赋值最终调用 `sub_40D5E0(type, value, index)`，字符串赋值最终调用 `sub_40D710(value, type, index)`。已看到的更新子码包括：

```text
0x41  +=
0x42  -=
0x43  *=
0x44  /=
0x45  %=
0x46  &=
0x47  |=
```

字符串左值只接受直接赋值或拼接赋值一类操作，非法组合会让 `sub_40D920` 返回 0。

## 11. 调用参数块：sub_410E30

`sub_410E30` 用于脚本调用、进入其他 HXB 资源等 handler。它解析一个以 `0x00` 结束的参数描述流。

格式大致是：

```text
[param_kind] expression_ff [param_kind] expression_ff ... 0x00
```

其中：

- `param_kind == 1`：期望字符串表达式，结果写入字符串空间 19，即 `dword_499984`；
- 其他值：期望数值表达式，结果依次写入 `dword_499980`。

解析完成后：

```text
dword_499980[254] = 字符串参数数量
dword_499980[255] = 数值参数数量
```

这说明 `dword_499980` 不只是普通变量表，也承担函数调用/脚本调用的参数寄存器职责。

## 12. 控制流指令

HXB VM 的跳转目标使用 24-bit big-endian 绝对 PC 偏移。偏移不是相对当前指令，而是直接写入当前 HXB 对象的 PC。

### 12.1 无条件跳转：opcode 0x29

`sub_4111D0` 处理 opcode `0x29`。格式：

```text
29 aa bb cc
```

执行时先让 PC 前进 3 字节，再按 big-endian 读取刚越过的 3 字节：

```text
target = aa << 16 | bb << 8 | cc
PC = target
```

### 12.2 条件跳转：opcode 0x26 / 0x27 / 0x28

`0x26` 由 `sub_411070` 处理：

```text
26 expression_ff aa bb cc
```

若表达式解析失败或结果为 0，则只跳过 3 字节目标；若表达式为非 0，则读取 24-bit 目标并跳转。若表达式结果是字符串，会报告类型错误。

`0x27` 由 `sub_411160` 处理，从结构上看是 `0x26` 的反向条件分支：表达式为假/零时跳转，为真时继续执行。

`0x28` 由 `sub_4110F0` 处理，包含表达式加两个 24-bit 目标，更像 if/else 双目标分支。需要结合样本进一步确认两个目标各自对应真分支还是假分支。

### 12.3 switch/table 跳转：opcode 0x2A

`sub_411200` 处理 opcode `0x2A`。格式大致为：

```text
2A expression_ff count_hi count_lo target_0 target_1 ... target_{count-1}
```

其中 count 是 16-bit big-endian。每个 target 是 24-bit big-endian，但 handler 中用 `v0 + base + 2*v0 + 2 + 1` 这种方式定位，实际表项长度应按 3 字节理解。

执行逻辑：

- 表达式值 `< 0` 或 `>= count`：跳过整个跳转表，继续执行表后面的代码；
- 否则读取对应下标的 24-bit 目标并跳转。

### 12.4 脚本内调用与返回：opcode 0x02 / 0x3C

`0x02` 由 `sub_4112A0` 处理，是脚本内 call：

```text
02 param_block aa bb cc
```

它先调用 `sub_410E30` 解析参数块，然后读取 24-bit 目标。当前 HXB 对象里有一个小调用栈：

```text
object[65804]        当前调用深度
object[65796..]      返回地址槽
最大深度             8
```

调用时保存当前 PC 为返回地址，然后 `PC = target`。

`0x3C` 由 `sub_411300` 处理，是 return：先解析一个返回表达式，把数值结果写入 `dword_499980[0]`，然后从调用栈弹出 PC。若调用栈为空，会报错。

### 12.5 退出当前 HXB 上下文：opcode 0x19 与顶层 0xFF

`0x19` 由 `sub_411380` 处理，会解析返回表达式并退出/弹出当前 HXB 包上下文，结果同样进入 `dword_499980[0]`。

顶层 opcode `0xFF` 不走普通 handler，而是在 `sub_410FC0` 中直接结束当前 HXB 包。两者都可能导致 `dword_4999C0` 切回上一个包对象。

## 13. HXB 包/资源切换相关指令

HXB 的 VM 可以把其他 HXB 资源作为新的执行上下文压入链表，因此它更像“脚本包 VM”，不只是单文件脚本。

### 13.1 进入已加载 HXB 资源：opcode 0x03

`sub_4135D0` 处理 opcode `0x03`：

1. 解析一个数值表达式作为资源 ID；
2. 调用 `sub_410E30` 解析参数块；
3. 根据资源 ID 找资源槽：
   - `0..199`：全局资源槽；
   - `200..255`：当前 HXB 对象局部资源槽；
4. 若槽类型为 `1`，说明该资源是 HXB，重置它的 PC 到自身 `data_start`，清空调用深度，并把它设为新的 `dword_4999C0`；
5. 若槽类型为 `9`，调用槽内对象的回调函数，更像插件/外部对象调用。

### 13.2 加载并挂入 HXB：opcode 0x06

`sub_413480` 处理 opcode `0x06`，会读取资源或路径，调用 `sub_40E930` 尝试按 HXB 解析，然后通过 `sub_40EB30` 挂入当前 HXB 包链。它是“加载新 HXB 包”的关键 handler。

### 13.3 加载普通资源：opcode 0x2C

`sub_411400` 处理 opcode `0x2C`，解析资源 ID 后调用 `sub_40EFF0`。`sub_40EFF0` 会先尝试 HXB，再尝试图片、音频或原始资源，因此 opcode `0x2C` 是脚本层显式加载资源的入口之一。

## 15. 对反汇编器/汇编器的影响

如果后续要按项目规范实现 HXB 字节码反汇编器，应把当前 VM 分成两层处理。

第一层是顶层 opcode 流：

```text
pc:
  optional_ext_prefix?    仅当 object + 263903 为真时存在，2 字节
  opcode                  1 字节
  operands                由具体 handler 决定
```

第二层是表达式流：

```text
expression := token* 0xFF
```

所有调用 `sub_40D920` 的 handler，都不应该用固定长度硬切操作数，而应先解析到表达式终止符 `0xFF`，再继续读取 handler 自己的剩余字段。例如：

```text
0x26  expression_ff  target24
0x29  target24
0x2A  expression_ff  count16  target24[count]
0x02  param_block    target24
0x3C  expression_ff
```

标签化策略也应按 24-bit 绝对 PC 实现：

- `0x26..0x2A` 和 `0x02` 的目标都应生成 `loc_XXXXXX` 标签；
- 反汇编文本中不要直接暴露硬编码目标数字作为最终语义；
- 汇编时由标签重新计算 24-bit big-endian 目标。

变量命名建议：

```text
NREG[i]     dword_499980，结果/参数寄存器
NLOCAL[i]   当前 HXB 局部数值变量
NGLOBAL[i]  全局数值变量
SARG[i]     字符串参数/返回字符串空间 19
SLOCAL[i]   当前 HXB 局部字符串
SGLOBAL[i]  字符串空间 18
```

表达式可以先用栈式伪代码输出，后续再逐步提升为更可读的中缀表达式。例如：

```text
.expr_push_i32 123
.expr_push_nlocal 4
.expr_add
.expr_store_nglobal 2
```

这样最容易保证零突变重建；等 opcode 和表达式覆盖稳定后，再做语义化美化。

## 16. 当前已确认与待确认点

已确认：

- HXB magic 规则为 `DD??HXB\0`，常见样本是 `DDWuHXB\0`；
- offset `0x08..0x0A` 是 24-bit big-endian 文件总长度；
- offset `0x0B` 是扩展头/名称区是否存在的标记；
- offset `0x10` 后主体 dword 使用固定公式按文件长度派生 key 后 XOR 解密；
- DDWu 影响扩展头字符串和表达式内联字符串的读取方式，宽字符串为 UTF-16LE 0 结尾；
- HXB 对象包含 56 个局部资源槽，对应资源 ID `200..255`；
- 脚本 VM 的单步解释器是 `sub_410FC0`，主循环是 `sub_410580`；
- 顶层 opcode `0xFF` 结束当前 HXB 上下文；
- 表达式解析器是 `sub_40D920`，表达式以 `0xFF` 结束；
- 跳转、调用、switch 目标使用 24-bit big-endian 绝对 PC；
- 数值变量至少有结果/参数寄存器、HXB 局部、全局三类空间；
- 字符串变量至少有 HXB 局部、字符串空间 18、字符串空间 19 三类空间。

待继续逆向确认：

- offset `0x0C..0x0F` 的具体语义；
- `object + 263903` 扩展模式下，每条指令前 2 字节前缀的真实含义；
- 解密主体开头是否总是脚本入口，或是否存在资源目录/初始化表；
- `(file_size - 13) / 4` 对尾部 1 到 3 个字节的真实处理方式，是否依赖文件整体对齐或分配冗余；
- 资源槽表在后续代码中如何由 HXB 主体填充；
- `0x00..0x5F` 中尚未命名 opcode 的具体语义；
- `0x28` 双目标条件分支两个 target 的真假分支顺序；
- `0x2A` switch 跳转表的边界细节，需要用样本 PC 做一次实测验证。

## 17. 后续实现建议

若要写 HXB 解析器，建议先实现最小验证流程：

1. 读取文件，检查 `DD??HXB\0` 和 24-bit 长度；
2. 判断 `is_wide` 和 `has_extended_header`；
3. 按 32-bit 截断计算 XOR key；
4. 从 offset `0x10` 解密 dword 主体；
5. 根据 `has_extended_header` 计算 `data_start`；
6. 从 `data_start` 开始按 VM 规则做保守反汇编；
7. 对所有 `target24` 建标签；
8. 对所有表达式先输出栈式语义，保证可重汇编。

伪代码：

```python
def parse_hxb(data: bytes):
    if len(data) < 16:
        raise ValueError("HXB too small")
    if data[0:2] != b"DD" or data[4:8] != b"HXB\0":
        raise ValueError("not HXB")

    size = (data[8] << 16) | (data[9] << 8) | data[10]
    if size != len(data):
        raise ValueError("HXB size mismatch")

    is_wide = data[2:4] == b"Wu"
    has_extended_header = data[11] != 0

    key = (((size + 455497) * (((32 * size) & 0xffffffff) ^ 0xA5)) ^ 0x34A9B129) & 0xffffffff

    plain = bytearray(data)
    for off in range(16, len(data) - 3, 4):
        value = int.from_bytes(data[off:off + 4], "little")
        plain[off:off + 4] = (value ^ key).to_bytes(4, "little")

    data_start = 16
    if has_extended_header:
        if is_wide:
            data_start = skip_two_utf16le_nul_strings(plain, 16)
        else:
            data_start = skip_two_nul_strings(plain, 16)

    return plain, data_start
```
