# Aoi `box`/`txt` 格式与 opcode 逆向笔记

本文根据 `export-for-ai/decompile` 中的 IDA 反编译结果整理，目标是回答两件事：

1. `box` 文件到底怎么被 exe 读取。
2. `box` 里的编译后 `txt` 脚本有哪些有效 opcode、参数个数是多少、作用大概是什么。

## 证据来源

- `sub_430F90` / `sub_42B740` / `sub_42B3B0`：`box` 打开、目录解析、数据读取。
- `sub_430D60` / `sub_42E6D0`：脚本主解释器。
- `sub_42CE20` / `sub_42CB30`：参数读取器。
- `sub_42AA90`：opcode 名称表。
- `byte_454AA0`：opcode 参数个数表，位于内存地址 `0x454AA0`。
- `aoi_archive_tool.py`：当前仓库里对 `AOIMY01` 解包/封包算法的重建实现。
- `aoi_mya_script_tool.py`：当前仓库里对编译后 `txt` 中文本段的提取实现。

## 1. `box` 文件格式

### 1.1 已确认格式

本作当前样本 `init.box` / `pro.box` / `quiz.box` 使用的是 `AOIMY01` ANSI 变体。

文件整体结构：

```text
0x00  8 bytes   signature = "AOIMY01\0"
0x08  4 bytes   file_count (big endian)
0x0C  4 bytes   reserved
0x10  ...       file entries
...             file data blocks
```

### 1.2 目录项结构

每个目录项固定 `0x18` 字节：

```text
0x00  12 bytes  name (cp932, zero-terminated/padded)
0x0C   4 bytes  extra/reserved
0x10   4 bytes  data offset (big endian)
0x14   4 bytes  data size   (big endian)
```

已知事实：

- 文件名字段长度是 `12` 字节，不是 `16` 字节。
- 目录项总大小是 `24` 字节。
- `extra` 字段在封包工具里默认写成 `1`，exe 读取时不参与主逻辑。
- 文件名编码看起来是 `cp932`/ANSI。

### 1.3 数据区加密

目录项指向的数据块不是明文，exe 读出来后会按“文件内绝对偏移”逐字节异或解密。

伪代码：

```python
offset = entry.offset
for i in range(entry.size):
    data[i] ^= key_from_offset(offset)
    offset += 1
```

密钥生成算法已经在仓库里重建：

- `aoi_archive_tool.py:key_from_offset()`
- `aoi_archive_tool.py:crypt_with_offset()`

这和 `sub_42B740` 中的解密循环一致。

### 1.4 exe 的读取路径

高层调用链如下：

```text
sub_41C710 -> sub_430F90(..., "pro.box", ...)
sub_41C6D0 -> sub_430F90(..., "init.box", ...)
sub_4157E0 -> sub_430F90(..., "quiz.box", ...)

sub_430F90 -> sub_42B740
sub_42B740 -> AgsFileSystemCreateFile + ReadFile + decrypt
```

`sub_42B740` 的职责：

1. 打开 `box`。
2. 检查头 `AOIMY01`。
3. 读取全部目录项。
4. 根据传入的索引 `a4` 选择某个目录项。
5. 跳到数据区读出 `size` 字节。
6. 用 `offset` 作为初始值逐字节异或解密。
7. 把解密后的整段缓冲区挂到脚本执行上下文。

## 2. 编译后 `txt` 脚本格式

### 2.1 本质

`box` 里的 `*.txt` 不是明文文本，而是“事件脚本字节码”。

exe 读取顺序：

```text
box -> 取出某个 txt 数据块 -> 解密 -> 作为字节码缓冲区 -> sub_42E6D0 逐 opcode 解释
```

### 2.2 主解释循环

主循环位于 `sub_42E6D0`：

```text
read 1 byte opcode
pc += 1
根据 byte_454AA0[opcode] 读取 N 个参数
switch(opcode)
执行该 opcode 的逻辑
```

结束 opcode 是：

- `0x78` / `120` / `@EXIT`

### 2.3 文本片段

虽然整个 `txt` 是字节码，但文本内容会以内嵌段的形式出现。当前仓库里的 `aoi_mya_script_tool.py` 已确认以下文本标记：

- `03 88 len text...`：名字文本
- `02 88 len text...`：对话文本
- `BC 88 len text...`：另一种对话文本

因此一个编译后 `txt` 可以理解为：

- “opcode 流”
- 加上若干内嵌的“长度前缀文本段”

## 3. 参数编码模型

### 3.1 参数个数表

每个 opcode 的参数个数来自 `byte_454AA0[opcode]`。

这个表本身不描述“参数类型”，只描述“该 opcode 后面要读多少个参数描述块”。

### 3.2 参数运行时结构

`sub_42CE20` 会把每个参数解析成一个 `12` 字节的运行时结构：

```text
struct Arg {
    int value_or_index;
    void* str_ptr_or_extra;
    uint8_t flags;
}
```

### 3.3 参数基础类型

`flags` 的基础类别至少包括：

- `0x02`：数值型
- `0x04`：布尔型
- `0x08`：字符串型

### 3.4 立即数 vs 引用

`flags` 的符号位决定它是“立即数”还是“变量引用”：

- `flags < 0`：立即值
- `flags >= 0`：需要进一步解引用/求值

对应求值函数：

- `sub_42C4C0()`：把参数求成整数
- `sub_42C540()`：把参数求成字符串
- `sub_42C610()`：把参数当条件判断真假

### 3.5 变量域

调试打印函数 `sub_42C660()` 暗示参数还区分变量域：

- `C`：数值
- `F`：布尔
- `S`：字符串
- `G`：全局域
- `L`：局部域

调试输出会组合成类似：

- `CG%d`
- `CL%d`
- `FG%d`
- `FL%d`
- `SG%d`
- `SL%d`

因此可以合理推测：

- 这套脚本同时支持全局变量和局部变量。
- 同一个参数槽里既可以放立即数，也可以放变量引用。

## 4. 核心 opcode 详解

下面这部分是主解释器 `sub_42E6D0` 直接处理的 opcode。

记号说明：

- `p1/p2/...` 表示第几个参数。
- “确定”表示能从本地 case 和被调函数确认。
- “推测”表示名字和调用关系都较强，但细节还可能有偏差。

| opcode | 助记符 | 参数个数 | 参数说明 | 作用 |
| --- | --- | ---: | --- | --- |
| `0x00` | `@NON` | 0 | 无 | 名字表里存在，但主 `switch` 没有显式 case，可能是空操作或保留指令。 |
| `0x02` | `@TEXT` | 1 | `p1=字符串` | 把文本追加到当前消息缓冲，经过 `sub_42E470()` 做变量替换/格式化。 |
| `0x03` | `@NAME` | 2 | `p1=名字字符串`，`p2=附加字符串/副标题(可空)` | 设置当前说话人名字。第二参数确实被读取，但具体显示语义仍待确认。 |
| `0x05` | `@CR` | 0 | 无 | 触发当前文本页/当前行的提交与显示，属于文本输出控制指令。 |
| `0x07` | `@SELECT` | 4 | `p1=分支值/目标`，`p2=选项文本`，`p3=附加值/条件`，`p4=启用标志或权重` | 向选择菜单注册一个选项。`p2` 确定是文本，其余 3 个数值参数的精确含义仍有待跑样本确认。 |
| `0x0A` | `@SET` | 2 | `p1=目标变量`，`p2=源值` | 赋值。支持数值/布尔/字符串。 |
| `0x0B` | `@ADD` | 3 | `p1=目标`，`p2=右值`，`p3=可选左值` | 加法或字符串拼接。若 `p3` 缺省，效果近似 `p1 = p1 + p2`；若 `p3` 存在，效果近似 `p1 = p2 + p3`。 |
| `0x0C` | `@SUB` | 3 | `p1=目标`，`p2=右值`，`p3=可选左值` | 减法。规则与 `@ADD` 同族。 |
| `0x0D` | `@MUL` | 3 | `p1=目标`，`p2=右值`，`p3=可选左值` | 乘法。 |

| `0x16` | `@GOSUB` | 1 | `p1=跳转地址` | 子过程调用，当前 `pc` 入栈后跳转。 |
| `0x17` | `@RETURN` | 0 | 无 | 从 `@GOSUB` 返回。若调用栈为空，会走异常/结束路径。 |
| `0x18` | `@SIL_GOTO` | 1 | `p1=跳转地址` | 静默跳转。和 `@GOTO` 一样改 `pc`，但名字暗示不会触发某些界面/日志行为。 |
| `0x1A` | `@IF` | 2 | `p1=条件`，`p2=跳转地址` | 条件为假时跳到 `p2`。 |
| `0x1C` | `@ELSEIF` | 2 | `p1=条件`，`p2=跳转地址` | 行为和 `@IF` 同族。 |
| `0x20` | `@LOOP` | 5 | `p1=循环变量`，`p2=终止值`，`p3=初始值`，`p4=步长`，`p5=退出跳转地址` | 一个计数循环原语。首次进入时把 `p1` 设为 `p3` 或 `0`，继续时加 `p4` 或 `1`，当达到 `p2` 时跳到 `p5`。 |
| `0x22` | `@WHILE` | 2 | `p1=条件`，`p2=跳转地址` | 条件为假时跳到 `p2`。 |
| `0x24` | `@NEXT` | 1 | `p1=循环头地址` | 跳回循环头，并把内部“继续循环”标志设为 1。 |

## 5. 扩展 / 游戏专有 opcode

这些 opcode 在 `sub_42AA90` 里有名字，在 `byte_454AA0` 里有参数个数，但 `sub_42E6D0` 没有本地 `case`。

因此它们大概率由：

- `v97` 游戏侧回调
- 或主解释器的 default 分支

来完成真正逻辑。

也就是说：

- 参数个数是“已确认”的。
- 作用多数只能依据助记符名字做“高置信推测”。

## 6. 有效 opcode 的判断规则

逆向过程中要注意一件事：

- “参数个数为 0” 不等于 “无效 opcode”。

因此更稳妥的判断方式是：

1. 若 `sub_42AA90` 里有助记符，则该 opcode 至少在调试层面被承认。
2. 若 `byte_454AA0[opcode]` 存在条目，则它的参数个数可被确定。
3. 若 `sub_42E6D0` 里有 `case`，说明它是主解释器直接处理的核心指令。
4. 若只有名字表但没有本地 `case`，则大概率是游戏逻辑回调处理的扩展指令。

## 7. 当前仍不确定的点

以下内容已经接近可用，但还没有完全实锤：

- `@SELECT` 四个参数中，数值参数各自到底是“跳转目标 / 结果值 / 启用条件 / 权重”的哪一种。
- `@NAME` 第二个字符串参数的 UI 语义。
- `@RUN` 和 `@GOTITLE` 在游戏层回调配合下的最终行为。
- 所有 `0x8A..0xF5` 扩展 opcode 的精确效果和返回语义。

## 8. 后续建议

如果要继续补完，最有效的路径是：

1. 给 `sub_42E6D0` 做一份“case -> 被调函数 -> 参数来源”的图。
2. 找到 `v97` 的真实函数地址和实现，补全扩展 opcode。
3. 对一两个样本 `txt` 做逐字节反汇编，把 `@TEXT/@IF/@EVNT` 这些高频指令和实际脚本内容对上。
